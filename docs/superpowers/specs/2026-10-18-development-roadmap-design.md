## 2. 保持不变的约束

- MCP SDK 固定为 mcp==2.3.0；不修改全局 Python、旧插件或正常项目配置。
- Mem0 是非核心正文、摘要和控制集合的持久来源；插件本地只保存标识、状态、指纹和锁。
- 完整 additionalContext 默认不超过 8192 UTF-8 字节，包含固定协议、项目核心、句柄、标记及区域包装；不是 token 预算。
- 核心自身超预算时失败，不截断核心；非核心按 P1/P2/P3、最旧 U、ASCII ID 顺序整条淘汰。
- 仅确认的有效采用推进 U；查询、读取、恢复、压缩和同一逻辑操作重试不推进 U。
- pending/unknown 不是成功；先定案原操作，不因搜索暂时无命中另起写入。
- 同项目经验可在 Codex 与 Claude Code 间共享；回执、句柄、U、窗口和检查点不跨宿主会话共享。
- 可信身份来自经过核验的宿主通道，不来自工具参数、任意句柄、启动 cwd 或历史会话扫描。
- 支持范围限单机器协调写入；不声明远端事务、CAS、跨机器锁或断电耐久。
- 信任本机 Codex 及获授权的 app-server 客户端；不宣称解析器识别任意恶意客户端编造的一致 metadata。
- 原生启用、在线合成写入及项目切换分别取得范围明确的授权。
- 不打包、不发布；未经明确要求不提交、推送或创建 Git 远程。

## 4. 最近一期：C1-E 有界执行器

### 4.1 方案选择

**推荐：夹具业务门禁 + 外部执行监督。** 内层保证不合规请求不进入真实服务；外层限制原生尝试、时长和整个任务的证据条件。现有身份解析/绑定/五工具复用，所有新增能力位于 scripts 与 tests/fixtures，不改生产入口。

仅用 CLI 事件监听更短，但只能在宿主已经发起调用后反应，不能保证第六次未进入服务；不作为硬调用限制。直接改生产并连接真实 Mem0，会将身份、持久化、恢复与安装同时混在一起，扩大写入和回退范围，也不推荐。

### 4.2 两层限制与可保证的范围

**内层：仅 bounded 模式启用的夹具门禁。**

1. 在真实服务调用之前串行检查：固定根、同一原生会话、有效且不重复的请求关联 ID、工具、参数、当前步骤。
2. 引导步骤成功后，仅保存当前/两个种子句柄的进程内值用于校验。参数集合精确限定；身份仍来自传输 `_meta`，不能由参数提供。
3. 同项目种子和外项目种子的 `SESSION_INVALID` 是第 3/4 步的预期业务结果，按步骤完成记录；其他失败不会被改写成该拒绝码。
4. 第六次、重复引导、并发第二次、错序、其他工具、身份切换或不符结果使场景冻结；在业务前拒绝，不再放行后续调用。
5. 门禁锁覆盖检查、执行、结果核对、脱敏审计和步骤提交。审计失败即 unknown，不继续。

**外层：有界执行器。** 默认仅离线/dry-run；每次明确选择一个项目。授权记录、安装回执、源码/配置摘要、当前宿主状态全部符合后，先保留尝试名额，再创建原生进程。每项目最多一个名额，整轮最多两个；任何已保留但结果缺失的尝试都不自动返还。

180 秒是原生子进程启动后的单任务截止时间，不是模型 token 或账单的硬上限。执行器能停止自己启动的进程并核验退出，不能阻止模型提出额外工具请求或保证操作系统瞬时终止；内层负责让额外请求不进入业务。不能确认子进程树停止时记 unknown、停止整轮，不声称完整清理。

### 4.3 固定五步协议

| 步骤 | 唯一允许动作 | 必须核验的业务结果 |
| --- | --- | --- |
| 1 | c1_bootstrap(本轮 nonce) | ready；当前根/会话；内存后端；两个种子 owner_status_verified 严格为 true |
| 2 | memory_status(当前句柄) | succeeded 严格为 true；当前会话/项目；U 严格为整数 0；活动项为空 |
| 3 | memory_status(同项目种子句柄) | 真实服务抛出 SESSION_INVALID |
| 4 | memory_status(外项目种子句柄) | 真实服务抛出 SESSION_INVALID |
| 5 | memory_status(当前句柄) | 同第 2 步，证明拒绝后当前身份仍有效 |

`memory_search/read/write/use` 在 bounded 模式全部业务前拒绝。保留普通夹具模式用于既有 SDK 全工具合同；生产 `create_server`、应用服务和域错误码不为探针修改。

### 4.4 状态与文件边界

状态：reviewed → installed → preflight_ready → attempt_reserved → running → verified / failed / unknown。前置不符是 blocked，未保留名额不计模型尝试；保留后任何失败保守计数。verified 只表示本场景，不升级 C1 整体。

被动 `launch-review.json` 不修改授权状态；源码或配置变化后生成全新 bundle，旧材料保留。安装只对当前 bundle 两个带标记合成根创建新 `.codex/config.toml`；已有文件、外链或变化一律拒绝。旧 review-only verify 在安装后继续拒绝，新增独立 installed 校验，不增加 skip-checks。

安装回执记录源清单摘要、根/标记与目标配置摘要；账本在模型启动前记录保留名额；运行结果、失败和授权记录分别保存。它们只包含标识/状态/哈希，不保存非核心正文或完整模型流。授权记录是已获用户确认的审计材料，不是任意客户端的认证令牌，也不因文件写着 true 就获得人类授权。

回退只删除本轮新建且字节仍与安装回执一致的配置；目标有变化则保留并报告冲突，不覆盖用户修改，不删除根/标记/审计/账本，不修改全局信任。

### 4.5 宿主预检

仅允许确切版本检查和以下 app-server 方法：initialize、initialized、config/read、hooks/list、account/rateLimits/read。预检绝不发送 thread/start 或 turn/start。RPC 整体和每条消息有时限/字节限制；未知、重复键、缺字段和不认识的模式均拒绝。

以有效 config 及层来源交叉检查：只有合成 MCP，命令/args 与已审阅预览完全一致；项目层受信任且生效；Hook、旧插件和非必要工具确实禁用；ordinaryUsageAllowed 严格为 true。禁用旧列表不足以证明未来新入口也禁用，出现未知启用项即停止。

启动时保留正常 on-request 审批和 read-only sandbox、--no-daemon/ephemeral 隔离；移除子进程 MEM0_API_KEY，不读注册表凭据，不切换模型/账户或开启额度回退。目标版本 0.163.0 只是已支持合同，不意味着本机当前仍是该版本；漂移先停止并重审。

### 4.6 结果和证据

夹具在真实服务外侧写入白名单业务结果审计：步骤、调用关联 ID 的摘要、工具、参数摘要、会话/根哈希、结果类别、允许的错误码和 U。原有 transport audit 仍只证明解析，不能替代业务结果。

执行器分别保存原生 item ID 与传输 callId 的摘要。**不假定两者相同**；先按精确版本结构建立映射，或在串行五步下以步骤、工具、规范参数摘要及各自唯一 ID 建立一一对应，存在歧义就 unknown。

原生 item.status=completed 不等于记忆操作成功，isError=true 也不一定意味着整个场景失败：两条 SESSION_INVALID 正是预期。只有真实 DTO/错误、五步门禁审计、原生调用完成、thread/根关联、退出码 0、turn.completed 同时成立才 verified。模型结束标记仅辅助，不作成功依据。

stdout/stderr 只在内存受限解析，不保存全流；正文、凭据和异常原文不进报告。无法识别的事件保存类别/字节数/哈希并停止，不为凑成功猜字段。

## 5. C1-N / C1-P：不要合并三种身份结论

1. **本地合同已完成**：SDK 测试用构造 metadata 证明解析/拒绝逻辑。
2. **下一次原生合成验证**：真实 Codex metadata 经服务，拒绝仍有效的合成种子；当前尚未执行。
3. **生产候选验收**：原生会话初始化与真实持久绑定、跨进程仍有效的原生句柄/读取回执及跨项目拒绝。合成内存后端不能证明此项。

C1-P 单独设计生命周期：fixture bootstrap 不进入公共工具；复用真正 SessionStart/绑定用例。即使仅初始化控制记录也属于真实 Mem0 写入，须明确合成 app/agent、操作清单和原操作续接规则，另行授权。生产身份和严格恢复分别标记能力，不用一个 verified 布尔开关同时放开所有功能。

## 6. C2：先合同可行性，后恢复适配

先收集目标版本实际的压缩触发/唯一边界/恢复事件与下一次模型请求关系。一个 turn_id 或 session_id + trigger 不自动等于唯一压缩边界。不得靠“最近一次 ready”或本地顺序猜测。

必须覆盖手动、自动、独立连续两次；完整 additionalContext 的 8192 UTF-8 字节、UTF-8 中文/边界、完整请求送达与输出截断/落盘；失效/淘汰不复活、U 不刷新；当前检查点 pending/unknown/P1 失败及应用发布中断。正常 Hook 输出与真实模型请求取证分开。

只使用受支持且经审阅的宿主诊断途径，不保存凭据或任意历史 transcript，不使用 TLS/权限绕过。无法取得必要请求证据或失败控制语义时明确 unverified/unsupported；可继续内核开发，但不能发布严格恢复声明。

## 7. H1：保留共享经验，版本化隔离控制

项目键保持宿主无关。控制身份显式包含 host_kind、machine_id、native_root_session_id；回执、窗口、U、检查点和会话操作幂等键归属于完整身份。具体编码在 H1 计划中统一定义，不在 Codex 单次探针里提前更改。

两个宿主必须使用共同可信协调目录的项目写锁，不能各自在不同 PLUGIN_DATA 持锁就宣称互斥。测试同名 session/operation ID、同时启动/维护、失效与恢复竞争、单端停用。旧指针模式不静默解释为新绑定，不复制旧活动集合；明确拒绝并经审阅重新绑定，经验数据不自动迁移。

## 8. A1/A2：Claude Code 按能力拆分

重新核对实际目标版本，不直接继承 2026-10-15 文档快照。A1 分别回答：外部 stdio 的可信逐请求会话身份；连续压缩唯一关联；立即注入；必要失败控制；输出上限与额外落盘；入口/Hook 合并与重复注册。

若只能满足记忆工具而不能严格恢复，就分别记录 supported/unverified/unsupported，经用户审阅决定能力范围；不因某一 Hook 能触发就宣称全部支持。不用可读句柄文件、工具自报身份或遍历历史作为可信桥接。确需桥接时另写完整的请求关联、有效期、防重放与跨会话拒绝设计。

A2 只实施可行能力：独立 Claude manifest/MCP/Hook 入口，共享内核；Codex 的 hooks/hooks.json 不因增加 Claude 清单自动在另一个宿主运行。保持唯一 bootstrap 和依赖方向，不引入动态宿主注册框架。

## 9. X1 与发布前检查

在两个宿主各自能力通过门槛后，执行同项目 A 写/B 读并重新采用、回执不能跨宿主使用、相同 EXP-ID 跨项目拒绝、A 失效后 B 不恢复旧版本、同机维护冲突、单端停用及逐项目回退。

正常项目切换前必须有精确配置差异、唯一记忆责任方及可执行回退记录；保留云端数据，不全局卸载旧插件或删除旧缓存。不把合成成功当正常项目迁移授权，不增加打包/marketplace 发布步骤。
